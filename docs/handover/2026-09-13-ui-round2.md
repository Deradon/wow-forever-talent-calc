# Handover: UI round 2 - the `#/changes` page, level, shortcuts, print, embed

The tail of round 2 in `docs/briefs/ui-improvements.md`: ideas 13 and 12 (the
`#/changes` page and `sel=` deep links), 10 (level slider), 14 (shortcut
overlay), 15 (print view) and 16 (embed mode). Idea 11, the desktop inspector
panel, was **not built**, on the brief's own terms: the nested sticky tooltips
(`docs/handover/2026-09-13-nested-tooltips.md`) already give a mouse-reachable,
pinnable card, and a second renderer of talent text is exactly what the brief's
section 6 warns against. `sel=` therefore pins the tooltip rather than filling
an inspector, which is the same feature with one renderer instead of two.

Web only. Nothing under `data/` or `pipeline/` was touched; `data/` was not read
directly - the generated `src/data/classic-diff.json` and `classic-text.json`
are the only sources of the diff.

Verified green: `cd web && npx vitest run` (348 tests, 21 files), `npm run build`
(type-check included), `npx playwright test` (65 tests, 11 of them new).
Nothing committed.

## 1. `#/changes` and `#/changes/<class>`

Two routes, one lazily loaded component (`web/src/ui/ChangesPage.tsx`), its own
chunk and its own stylesheet (`changes.css`), so a player who only ever opens a
class page pays nothing for it. The entry chunk went 123.6 -> 126.6 kB gzip,
which is the routing plus the level and shortcut code, not the page.

- **`#/changes`** is the overview: nine rows, six count columns (new, moved,
  ranks, reworked, values, gone) and a totals row - 145 / 81 / 26 / 127 / 22 /
  108. Every class name links to its list. Only classes that have a Classic
  counterpart appear, so the example classes are simply absent instead of
  claiming that all of their talents are new.
- **`#/changes/<class>`** is the list: the class strip, a filter box, a jump
  strip of six section chips with counts, then the six sections themselves.
  Sections follow the generator's precedence, so every talent appears in
  **exactly one** of them - a player counting "how much changed" must not be
  able to count the same talent twice. A move that also carried a rewrite says
  `Also reworked.` in its detail line rather than appearing twice.

The class strip is `ClassSwitcher` with two new optional props (`hrefFor`,
`hintFor`); nothing else about it changed, and the class page passes neither.

**The model is pure.** `web/src/ui/changesModel.ts` takes the class file, the
generated change map and the removed list and returns the six sections;
`ChangesPage` supplies all three. It never imports the generated JSON, which is
why `changesModel.test.ts` can drive the whole page model off the synthetic
`makeClass` fixture. The detail lines reuse `changeLine` and
`valuesChangedLine` from `tooltipText.ts`, so the page and the tooltip cannot
disagree about what changed; only the position (`Holy, row 3`, `Now in Holy.`)
is the page's own.

The word diff is rendered inline in the Classic sentence - dropped words struck,
added words marked on a faint plate - the same treatment as the tooltip's
nested card, down to the `.diff-del` / `.diff-add` class names. It comes from
`classic-text.json`, fetched with the same dynamic `import()` the card uses
(`loadClassicTexts`, added beside `loadClassicText`: whichever asks first pays,
the other gets it free). The page renders without it and fills the sentences in
when the chunk lands.

Entry points: the class header next to "What's new", the landing page in one
line under the caveat, and `#/changes` itself from either.

## 2. `sel=<talentId>`: one talent, deep linked

`web/src/url/route.ts` grew two optional class-route parameters, both view
state, both ignored by the codec, both written after `t=` so the shareable
prefix of a round-1 link is unchanged: `sel` and `embed`. `sel` is validated
against the same slug pattern as a class id, because it goes straight into a
`querySelector`.

The mechanics (`TalentCell`, one effect): a tooltip normally earns the pointer
by dwell **and** approach (`stickyTooltip.ts`); a link is a stronger statement
of intent than either, so `selected` skips straight to sticky - the card is
interactive, its nested terms are reachable, and it claims the single open slot
through `claimTooltip` like any other. Focus lands on the **cell**, not in the
card, so the arrow keys keep working. `ClassPage` switches to the talent's page
first when it is on another one, and scrolls it into view.

Closing is unchanged (Escape, the card's own background, hovering another
cell); what is new is that a pinned card that closes calls back up and
`ClassPage.deselect()` strips `sel` from the hash **as it stands**, with
`URLSearchParams` on the existing hash rather than by rebuilding it from the
build - so closing a tooltip can never silently rewrite a `t=` that needed
sanitizing.

## 3. Level: "points at level X"

`web/src/rules/level.ts`, pure and table-tested (`level.test.ts`, 6 cases):
`pointsAtLevel` is the exact inverse of `requiredLevel` (asserted for all 51
points), `levelRange` gives the slider its bounds from `rules.firstPointLevel`
and `rules.maxLevel`, `standingAtLevel` returns available / spent / affordable /
beyond, and `levelLine` is the one sentence the panel prints.

The control is in the summary column, defaulting to max level. It deliberately
**does not** mark individual talents: the order in which a build was spent is
not tracked - the link carries a set of ranks, not a history - so the only
honest statement is `At level 40 you have 31 of your 51 spent points - 20 too
many.` The brief asked for exactly this and it is worth keeping that way; a
"which talents are beyond your level" marker would need a spend order the URL
does not carry.

## 4. Shortcut overlay, print view, embed mode

- **`ShortcutsOverlay.tsx`**: `?` anywhere (ignored inside a text entry) or the
  small `?` button in the site header. A `role="dialog" aria-modal` panel, four
  groups covering every gesture rounds 1 and 1b shipped, focus moved in on open,
  Tab cycling inside, Escape (and `?`) closing, focus restored to the opener.
  It lives in `App.tsx`, so it is available on every route except an embed.
- **Print**: `src/ui/print.css`, imported from `index.css`. No `?view=print`
  route - a stylesheet is the whole feature and Ctrl+P works from wherever the
  player is. It hides the controls, navigation, tooltips and hints, puts the
  trees on white at 34px cells (with `--arrow-scale` following), sets the
  summary list in three columns, keeps panels off page breaks and prints the
  build URL under the title from `data-print-link`. The **Print** button in the
  summary column calls `window.print()`.
- **Embed**: `#/<class>?embed=1`. `App` renders a bare shell (no site nav, no
  footer, no shortcut button, no skip link) and `ClassPage` drops its header,
  notices, hint line and summary column, leaving the page tabs, the trees at
  full width, and a one-line `EmbedBar`: `Paladin 31/0/20`, the points and the
  required level, and an "Open the full calculator" link that leaves the iframe.
  `embed=1` survives every edit, so the iframe stays an iframe. Documented with
  an `<iframe>` snippet in `web/README.md`, which also gained the new routes,
  the `sel=` contract and the print section.
