# Handover: `#/races` (Phase 2b web half)

Date 2026-09-13. Owner of this session: `web/` only. Nothing under `data/` or
`pipeline/` was touched; `data/races/` was read, never written. The spec is
section 5 of `docs/handover/2026-09-13-races-data.md`; where this page had to
choose, that section decided.

Verified green: `cd web && npx vitest run` (437 tests, 23 files), `npm run build`
(type-check included), `npx playwright test` (70 tests, 5 of them new). Nothing

## 1. The two routes

`#/races` and `#/races/<race>`, one lazily loaded component
(`web/src/ui/RacesPage.tsx`), its own chunk (22.4 kB raw / 6.4 kB gzip) and its
own stylesheet (`races.css`), exactly the arrangement `#/changes` has. A player
who only opens the calculator pays for neither.

- **`#/races`** is the matrix: one row per *playable identity*, one column per
  class in class-bar order, and a gold-ringed cell for every combination the
  Classic Era prior does not have (16 of them, which is 6 races plus the two
  Skyborne variants). Rows are grouped Alliance, then Horde, alphabetically
  inside a group - the arrangement of the character-creation screen the data was
  read from. A race name opens its page, a cell opens that class's calculator,
  and the trait count column links to the page too.
- **`#/races/<race>`** is the race: name, faction chip, the variant tabs when the
  race has variants, the class list as chips that link to the calculators, the
  provenance statement, the caveats, then the traits as cards and the lore in a
  closed `<details>`.

**One row per playable identity, not per race file.** The two Skyborne variants
have different class bars - High Order has Mage, Windshaper has Shaman - so a
single Skyborne row would claim a Skyborne Mage can join the Horde. They are two
rows, each on its own faction side, each linking to
`#/races/skyborne?variant=<id>`.

`variant` is view state on the hash, validated against the same slug pattern as
a class id. An unknown variant falls back to the Alliance one rather than
rendering an empty page, which is also what "no variant given" does.

**Races is linked from the site header** (next to a new `Changes` link, which
had no header entry before) and from the landing page in one line under the
existing `#/changes` line.

## 2. The rules the page had to follow, and where each one lives

Section 5 of the data handover lists eight. All eight are in
`web/src/ui/racesModel.ts`, pure and unit tested (`racesModel.test.ts`,
19 cases), so the page component computes nothing:

1. **`observed: false` or an empty class list is unknown, never "no classes".**
   `cellState` returns `unknown` and the cell renders `?` with a spoken label.
   No race is in that state today; the branch and its test are there for the
   first one that is.
2. **The trust statement is made once, at the top of the page, not per card.**
   Every one of the 37 traits is unreviewed with confidence 1.0, so 37 copies of
   one amber line would be noise, not honesty. `raceTrustLines` prints
   "Read from the stream by a vision model. None of the 4 traits here have been
   checked by a reviewer.", plus a second sentence when any trait is below the
   review threshold. A card that *is* below it still gets the tooltip's own
   amber line, through `trustLine` itself (section 3), so the two renderers
   cannot drift. Each card's `Details` carries `readingLine` - the stream
   timestamp - and a link to the frame crop.
3. **A trait with no description renders `source.note` instead of a blank.**
   None is in that state today.
4. **The Classic side is a paraphrase written from memory.** It is nested in a
   closed `<details>`, and the summary always carries the word `unverified` -
   including on a `new` trait, whose "no Classic racial of this name" claim
   comes from the same unverified prior. `classicNoteLines` keeps the reasoning
   and drops both the "written from memory" clause and the repo path the
   pipeline appends, because the label already says it and a player should not
   read a file path. A corpus test asserts no note is emptied by that cleaner.
5. **Traits render in `order`**, the order of the box.
6. **Icons are crops.** `raceCropUrl` resolves `iconCrop`; the fallback is the
   trait's initials, as in the talent grid. There is no crest crop for a race
   (stage 12 cuts trait icons and the panel, not the portrait ring), so the
   matrix rows show the race's initials; `raceCrestUrl` looks for
   `_crest.png` / `_portrait.png` so that dropping one file beside the panel
   crop is all it takes to light that column up.
7. **A variant shows its own traits, classes and lore**, never the union.
8. **`complete: false` and every `notes[]` entry are shown.** Nothing is
   `false` today, so the incomplete line has a design and no data.

The "new combination" rule is the one the data handover suggested: a class in
the race's bar that `data/prior/classic-era/racials.json` does not list for that
race. That prior is unverified, which the page says under the table. When the
prior knows nothing about a race at all, `newCombos` is `undefined` and the row
marks **nothing** - "the prior is silent" is not "everything is new".

## 3. `trust.ts`: one wording, three pages

`web/src/ui/tooltipText.ts` owned the amber trust line, the reading line, the
`internalId` guard and `withPeriod`. The races page needs all four and none of
the rest of that file, so they moved to `web/src/ui/trust.ts`, which imports
nothing - `REVIEW_THRESHOLD`, `streamStamp` and `needsReview` moved with them.
`tooltipText.ts` and `review.ts` re-export everything they used to define, so
every existing caller and every existing test is unchanged, and the tooltip, the
changes list and the races cards still get their wording from one function. A
second phrasing of "uncertain reading" is exactly what the text-quality review
warns against.

## 4. Two generated files, and what the fourth lazy route cost

`scripts/gen-data-index.mjs` gained a races half, regenerated on every dev
server, build and vitest run and asserted fresh by `generated.test.ts`:

- **`src/data/races-index.json`** (~7 kB) is the whole data source for the
  matrix: names, factions, variants with their own class lists, trait counts by
  Classic status, the new-combination flags and the matrix notes. The overview
  therefore fetches **no** race file and not `matrix.json` either.
- **`src/data/raceCrops.ts`** is 91 static `?url` imports - every racial icon
  crop, every trait row crop and the class-bar and panel evidence - so the races
  chunk carries its own crop URLs instead of the 971-entry review registry.

`matrix.json` is excluded from the race glob (`'!../../../data/races/matrix.json'`);
without that vite emits a chunk for a file nothing imports.

**The one regression, and why it is accepted.** Adding a fourth lazy route makes
rolldown split the modules the entry shares with the lazy routes (React itself,
`load.ts`, `title.ts`, `trust.ts`, `ClassIcon.tsx`) into shared chunks the entry
then fetches alongside itself: the landing page goes from one script to three,
and from 122.6 to about 126.5 kB gzip. It is the fourth route that does this, not
the sharing - a build with `RacesPage` lazy and importing nothing from `trust.ts`
splits the same way. `tests/landing.spec.ts` therefore no longer asserts "exactly
one script"; it asserts what it always meant - no class chunk, no `ReviewPage`,
no `ChangesPage`/`RacesPage`, no crop registry - plus a cap of four scripts.
`build.rollupOptions.output.experimentalMinChunkSize` does not help: vite 8 runs
rolldown, which rejects the option.
