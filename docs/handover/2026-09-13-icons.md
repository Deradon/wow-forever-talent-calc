# Handover: icon matching (stage 9)

Date: 2026-09-13. Scope: replace the 36 px screengrab icons by clean icon
files where a known icon matches; keep crops for genuinely new Forever icons.
Nothing has been applied yet: `data/extracted/*.candidates.json`,
`data/talents/` and `data/encoding/` are untouched (another workstream was
editing them). Everything is prepared, see "How to apply" below.

## What exists

- `pipeline/src/wowtalents/icons.py`: pure matching helpers (features, NCC
  scoring, pHash re-rank, Classic-prior hint, decision, `apply_matches`).
- `pipeline/stages/09_icons.py`: `refs` (reference list + download), `match`
  (crops -> `data/icons/matches.json`, optional contact sheets under
  `pipeline/work/icons/sheets/<class>.png`), `fetch` (56 px icons for
  accepted matches -> `web/public/icons/`), `apply` (icon fields into the
  candidates files).
- `pipeline/tests/test_icons.py` (synthetic icons and cells) and one new test
  in `tests/test_export.py` for the export change. Whole suite: `cd pipeline
  && uv run pytest -q`.
- `pipeline/src/wowtalents/export.py`: `_talent()` honours `icon` /
  `icon_source` on a candidate record (sets `icon`, `iconSource`, drops
  `iconCrop`). Backwards compatible: records without those fields export as
  before. This is the only change to existing code.
- `data/icons/matches.json`: one record per class and `<tree>/<talent-id>`
  (chosen icon, score, margin, pHash distance, method, confidence, reference
  tier, top-3 candidates, the candidate cell). `data/icons/SOURCES.md`:
  reference set, method, licensing.
- `web/public/icons/<name>.jpg`: 56 px icons of every accepted match.
- Reference set under `pipeline/work/icons/` (git-ignored): `lists/`
  (Wowhead talent data files, wago.tools manifest CSV, `reference.tsv`,
  `fetch.log`), `ref/<name>.jpg` (36 px), `sheets/`.

## Reference set

6,631 icon names in three tiers (`pipeline/work/icons/lists/reference.tsv`),
6,628 fetched as 36 px `medium` JPGs from Wowhead's CDN (3 names are not on
the CDN), one request at a time with a 0.3 s pause, no 403/429 seen:

| Tier | Names | Source |
|---|---|---|
| `prior` | 306 | icons of the 432 Classic Era talents (`data/prior/classic-era/talents.json`) |
| `later-talents` | 1,017 new | `"icon"` fields of Wowhead's TBC / Wrath / Cataclysm / MoP Classic talent data files |
| `classic-era-client` | 5,308 new | every `Interface\ICONS\*.blp` in `ManifestInterfaceData` of Classic Era build 1.15.9.69722 (wago.tools CSV) |

Details and licensing: `data/icons/SOURCES.md`. Full download takes about
70 minutes; `refs` skips files that exist, so re-runs are cheap. The Forever
client (1.60.x) is not on wago.tools yet; the day it is, its manifest (or
`Talent.db2` + `SpellIcon`) replaces the matching (`iconSource: "datamined"`).

`classic-prior` = the Classic talent of the same name supplied the icon and
the image agrees (top 3, NCC >= 0.45); `visual` = the image alone decided
(NCC >= 0.60 with a 0.04 margin over the first non-variant runner-up, or NCC
>= 0.80; pHash <= 26 unless NCC >= 0.80). A visual winner that contradicts a
Classic prior needs NCC >= 0.85 and a 0.10 margin, otherwise the crop is kept
(11 talents; e.g. Shatter and Improved Renew, where the best candidates were
a gem and a bandage). `high` = NCC >= 0.80 with margin, or the prior icon
ranked first; everything else `medium`.

**`apply` and `fetch` take `high` only by default** (397 talents, 312
distinct icons, all in `web/public/icons/`). The 30 `medium` matches stay in
`matches.json` for a human verdict; the sample below puts their precision
around 55 %, too low to ship unreviewed.

Available (green, full colour) cells: 71; the remaining 398 crops are
darkened, desaturated locked cells, which is why colour plays no role in the
matcher.

## Precision estimate

Three stratified samples were checked side by side (crop, contrast-stretched
crop, matched icon at 3x) with the Read tool and, as a second opinion, Codex
(`codex exec -i <sheet>`); sheets in `pipeline/work/icons/sheets/` and the
per-class sheets `match --sheet` writes.

- 20 matches from the first run (prior + later tiers only, before the
  client tier was fetched): own reading 19 yes / 1 unsure, Codex 15 yes /
  4 no / 1 unsure; every Codex "no" was a `medium` match.
- 30 matches stratified by confidence (15 high / 15 medium) with the full
  reference set: high 14-15 / 15 correct (both readers); medium 8 / 15 clear
  yes, 5 no (Booming Voice -> an ore, Mangle -> a throwing knife, Improved
  Renew -> a bandage, Blood-Crazed, Survivalist's Discipline), 2 unsure. The
  prior-contradiction rule added after this sample removes three of the five
  wrong ones (now "keep crop").
- 30 further high matches never sampled before, biased towards the riskier
  `visual` and `classic-era-client` ones (18 of 30): own reading 26 yes /
  3 unsure / 1 doubtful; Codex 27 yes / 3 no (same three items: Mutilate ->
  `ability_rogue_deadlybrew`, Improved Fire Nova -> `spell_fire_sealoffire`,
  Improved Regrowth -> `spell_nature_resistnature`). The last two are the
  Classic icons of those talents, so they are most likely right and the
  doubt comes from very dark crops.

Estimate: **high about 93-97 % correct** (roughly 12-25 wrong icons among
397, concentrated in `visual` matches of dark crops), **medium about 55 %**.
The 13 `classic-era-client` matches in `high` looked plausible (herb for
Overgrowth, horn for Voice of Truth, crossbow for Focused Fire, scroll for
Litany of Light, swords/spear/shield for weapon talents, class icon for
Cutthroat); item icons for talents are unusual, so they deserve a glance in
the review UI once matched icons render there (see "Web").

Low-contrast crops (inner std 2-4 on a 0-255 scale) were checked separately:
after contrast stretching they do show the structure and the matches held
up (e.g. Cold Snap, Purification and Efficiency all map to
`spell_frost_wizardmark`, which is the Classic icon of all three), so no
contrast guard was added.

## How to apply (not run yet)

From `pipeline/`, after the concurrent candidates/export work has landed:

```sh
uv run pytest -q                                   # 171 tests
uv run stages/09_icons.py match all --sheet        # refresh matches.json against current data/extracted/<class>.json
uv run stages/09_icons.py fetch                    # web/public/icons/<name>.jpg for every high match (skips existing; already done for the current set)
uv run stages/09_icons.py apply all --dry-run      # what would change
uv run stages/09_icons.py apply all                # icon / icon_source / icon_match into data/extracted/<class>.candidates.json (high only; --min-confidence medium for all)
for c in druid hunter mage paladin priest rogue shaman warlock warrior; do
  uv run stages/08_export.py extract $c && uv run stages/08_export.py promote $c
done
for c in druid hunter mage paladin priest rogue shaman warlock warrior; do uv run validate.py ../data/talents/$c.json --check; done
cd ../web && npm test                              # crops.test.ts / validateData.test.ts must stay green
```

`apply --dry-run` reports what would change. `match` is idempotent and reads
`data/icons/verified.json` if present: `{"paladin": {"holy/twilight-focus":
true}}` confirms (or accepts the best candidate of a rejected talent),
`false` retracts, an icon name string forces that icon (`method: "manual"`).
Re-running `match` after editing `verified.json` and then `apply` + export
propagates the verdict.

`apply` only touches `data/extracted/<class>.candidates.json`; `08_export.py
extract` rebuilds `data/extracted/<class>.json`, `promote` rebuilds
`data/talents/<class>.json` (reviewed talents keep their fields, so a
reviewed talent whose icon should change needs the icon in
`data/overrides/<class>.json` via `set`, or a re-review).

The candidates record gains three fields: `icon` (name), `icon_source`
(`classic`), `icon_match` (score, margin, phash, method, confidence, tier,
verified). Records without an accepted match lose those fields on the next
`apply` (a threshold change can retract).

## Schema note

`iconSource: "classic"` is documented as "pHash-matched against the Classic
icon set". The matcher uses the Classic Era *client's* icon set (which
includes icons first used in later expansions) plus later talent icons, with
NCC + pHash. Suggested wording for DATA-SCHEMA.md section 4.4: `classic` =
visually matched against the known icon set (Classic Era client), see
`data/icons/SOURCES.md`. No schema or validator change is needed: `icon` names
match `^[a-z0-9_-]+$`, `iconCrop` is dropped when `iconSource != "crop"` (rule
9), the crop PNG stays under `data/review/` because `source.crop` (the tooltip
crop) is unaffected and the `.icon.png` costs nothing to keep.

## Web

No code change is required for the switch:

- `web/src/ui/TalentCell.tsx` already resolves `iconSource !== 'crop'` to
  `${BASE_URL}icons/<icon>.jpg` and falls back to initials on load error;
  `web/src/ui/talents.css` applies `grayscale(1) brightness(0.5)` to locked
  cells for any `img`, so file icons get the locked look for free.
- `web/src/data/crops.test.ts` checks `iconCrop` only for `iconSource ===
  'crop'`; `validateData.test.ts` checks the iff rule; both stay green after
  export because `iconCrop` is dropped together with the source switch.
- `web/public/icons/` is copied verbatim by Vite; the files are ~3 kB each
  (56 px JPEG), all referenced ones together well under 2 MB.

Worth doing later (not blocking):

- `ReviewPage.tsx` shows the icon only for crops (`talent.iconSource ===
  'crop'`); for matched talents it prints the name. Rendering
  `icons/<icon>.jpg` next to the crop there would make the review of matches
  possible in the browser (crop and icon side by side, the `.icon.png` is
  still shipped).
- Crop icons are already dark for locked talents in the footage while file
  icons are bright; the locked filter now makes crops darker than file icons.
  The M3 note in `2026-09-13-web.md` (lighter filter for crops, or an
  autocontrast pass on the crops in the pipeline) becomes more visible once
  most cells are files.
- `web/README.md` "Icons and crops" mentions `pipeline/fetch_icons.py`; the
  actual command is `stages/09_icons.py fetch`.
