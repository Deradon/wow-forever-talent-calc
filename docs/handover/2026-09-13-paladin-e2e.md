## Error rate

Two checks. (a) 13 readings compared character by character against their
crops with the Read tool (10 random plus the three single-frame crops
Unyielding Faith, Sacred Arbiter, Illumination): 12 exact, 1 wrong.
(b) All 45 crops transcribed a second time with the local codex CLI
(`scripts/second_opinion.py`) and diffed on name, rank and description:
name and rank identical on 45/45, description identical on 38/45 (after
prompt v3; 40/45 before it, but with one substantive miss: Seal of Command
lost its whole second paragraph after the blank line, which both Qwen
passes agreed on). The 7 remaining differences are all one character and
all on Qwen's side where the crop was checked: mid-sentence words starting
with "In" capitalised (Consecrated Ground "Increased", Guardian's Favor
"Increases", Pursuit of Justice "Increasing", Seal of Command
"Incapacitated"), a comma read as a period (Sacred Duty), a period read as
a comma (Holy Shield, unverified which is right), and a dropped "%"
(Divine Precision "by 6." - a 3x pass read "6%" under prompt v2, under v3
both passes drop it again).

Estimate: about 15 % of records (7/45) carry a one-character defect in the
description, i.e. roughly 1 defect per 30 description lines; 0 errors in
names, ranks, `kind`, `requires`, `footer`, `extra_lines` across every
check; 1 substantive error (dropped paragraph) in 45 before prompt v3, 0
after. Two Qwen passes at different scales agree on almost every defect
(only Guardian's Favor was caught as 0.7 by the pair), so the pass-agreement
confidence of the brief measures determinism, not correctness; the codex
second opinion is what routes the defects into the review queue. All 7 are
now at confidence 0.7 with `source.note` "second reader (codex) differs in
description" and both readings in `source.readings`.

## Prompt used (reader.py, `PROMPT_VERSION = tooltip-v3`)

System: transcribe exactly, never paraphrase, ignore icons bleeding through
the box; the six line kinds top to bottom (name, "Rank N/M", white
Passive/cost/range/cast lines, red "Requires" lines, gold description of
one or more paragraphs possibly separated by a blank line, green footer);
field-by-field rules: `kind` is "Passive" only for a line reading exactly
Passive, `extra_lines` are the other white lines, `requires` only lines
starting with "Requires", `description` is all gold paragraphs in order
with line breaks and blank lines joined by spaces, nothing left out, without
the Passive/Requires/footer lines, original capitalisation kept
(mid-sentence words lowercase unless names), `footer` the green line,
`cut_off` true only when a line is visibly truncated or runs into the
border so words or a line are missing, a complete box with a margin is not
cut off. v2 -> v3 added the multi-paragraph and capitalisation sentences;
the paragraph fix worked, the capitalisation bias stayed. User message: a one-shot text
example (Toughness 0/5 -> the JSON) and "Now return the content of this
tooltip as JSON." Schema: `additionalProperties: false`, all fields
required, `kind` enum ["Passive", null]. The header prompt returns
`title, tabs[], active_tab, unspent_talents`; the tree-strip prompt
`name, points`.

## Open points

- `data/review/<class>/<tree>/` now holds both the provisional
  `r<row>c<col>.png` copies (stage 5, as before) and the slug-named copies
  made by stage 8 (`<talent-id>.png`, `.icon.png`); 3.5 MB for Paladin. One
  naming scheme should go once the review UI settles on ids.
- Rank anticipation needs a unit-aware rule ("1 min" vs Classic "60 sec")
  and should not accept token-subset name matches at similarity 1.0.
- Two Qwen passes at different scales are not independent readers: they
  agreed on every one-character defect but one. 3x/2x is the default now;
  the codex second opinion is the effective error detector. If codex is
  unavailable, a 4x third pass for descriptions that end a sentence with a
  bare number would at least catch dropped units.
- Qwen-4B capitalises mid-sentence words beginning with "In" (increases,
  incapacitated); a prompt sentence did not help. A post-rule would be
  hacky; leave it to review, or try the 8B model when VRAM allows.
- Rule 18 (tree too small for 51 points) fires for every tree; the `rules`
  block (51 points, 5 per row) is an assumption and may be wrong for
  Forever.
